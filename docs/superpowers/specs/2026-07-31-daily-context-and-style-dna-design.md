# 每日推荐上下文与 Style DNA 治理设计

## 目标

让“今日”页在用户打开应用时自动使用当前日期、位置、城市和天气生成推荐，并在每天
06:30 提前准备默认三套；同时把持续累积的灵感信号收敛成少量、稳定且可管理的 Style
DNA，避免色板失真和大量低质量标签干扰造型师。

本次保持 Stitch React 五页、导航和整体视觉不变，不引入新的前端依赖。

## 已选择方案

采用“设备提供位置、后端统一天气与城市、外部调度触发预生成、现有 Profile JSON 字段
承载标签偏好”的最小方案：

- 浏览器原生 `navigator.geolocation` 获取经纬度。
- 后端继续使用 Open-Meteo，并补充降雨字段。
- 后端低频调用 Nominatim 反向地理编码显示城市；结果缓存，定位失败时不阻断天气。
- 06:30 由部署环境的调度器调用内部预生成入口，不在 FastAPI 进程内造定时器。
- 不新增数据库表；复用 `profile.learned_from_feedback_json` 保存标签置顶、隐藏和合并规则，
  只给 `outfit_history` 增加一个推荐上下文字段。
- Style DNA 合并时只保留有限的核心标签和规范色名，推荐模型不再接收全部历史原始标签。

未选择的方案：

- 纯前端天气：会把多种外部接口、缓存和错误处理散落在页面中。
- FastAPI 进程内定时器：开发热重载或多进程部署会重复执行，主机休眠也无法保证 06:30。
- 新建标签、位置和推荐缓存表：v0 单用户无需为这些状态增加迁移和维护成本。

## 自动位置、日期与天气

### 前端流程

1. “今日”页首次打开时先读取设备当前日期，不使用硬编码日期；天气返回后以位置所在时区
   的 `local_date` 为准。
2. 读取本机缓存的最近一次成功定位。缓存存在时先用缓存渲染，再异步请求当前位置。
3. 调用 `navigator.geolocation.getCurrentPosition()`，只申请一次系统权限；成功后将经纬度
   四舍五入到小数点后三位再传给后端，避免保存过细位置。
4. 调用 `GET /api/weather?latitude=...&longitude=...`，界面显示城市、实时温度、天气和
   当日降雨提示。
5. 生成穿搭时把同一经纬度传给 `POST /api/recommend`，城市文本只用于展示和兜底，
   不作为定位成功后的天气查询依据。

本机缓存保存：

- 最近一次粗略经纬度；
- 最近一次成功识别的城市；
- 定位时间；
- 用户手动选择的备用城市。

定位缓存有效期为 24 小时。应用重新进入前台时可以刷新；本次不做持续位置监听。

### 后端天气响应

现有 `WeatherData` 增加：

- `city`：反向地理编码得到的城市；识别失败时为空；
- `local_date`：Open-Meteo 所在时区的当地日期；
- `timezone`：天气响应使用的时区；
- `precipitation`：当前降水量，单位 mm；
- `rain`：当前降雨量，单位 mm；
- `precipitation_probability_max`：当日最高降水概率；
- `precipitation_sum`：当日总降水量预测，单位 mm；
- `rain_window`：未来 12 小时内首段有显著降雨概率的本地时间范围，无降雨时为空。

Open-Meteo 请求继续使用 `timezone=auto`，增加 current、hourly 和 daily 降雨字段。天气
结果缓存 30 分钟；反向地理编码结果按粗略经纬度缓存 24 小时。

Nominatim 只由后端代理调用，使用明确的应用 `User-Agent`，限制为用户主动定位触发并
缓存结果。界面设置页保留 OpenStreetMap 署名。该公共服务只适用于当前个人/小规模
测试；正式开放给多人使用前必须换成有服务保证的反向地理编码服务。

### 失败与兜底顺序

1. 定位成功：使用当前粗略经纬度。
2. 定位被拒绝或超时：使用上次成功定位的粗略经纬度。
3. 没有历史定位：使用用户手动选择的城市。
4. 没有手动城市：使用 Profile 中保存的常住城市。
5. 全部缺失：提示“需要定位或选择城市”，不再默认东京。

反向地理编码失败只影响城市名称，天气仍按经纬度返回；天气接口失败时保留上次成功
天气并明确标注“上次更新”，不伪装为实时数据。

## 每天 06:30 默认三套

### 生成逻辑

- 调度时区使用 Profile 常住城市/最近定位对应时区；当前单用户默认
  `Asia/Shanghai`。
- 每天 06:30 调用内部预生成入口，使用最近一次成功的粗略经纬度、默认场景“日常”、
  无心情、无临时风格要求，生成 Safe / Fresh / Stretch 三套。
- 预生成结果复用现有 `outfit_history`：三条记录的 `action` 为 `prepared`，而不是
  `shown`。同一天同档只读取最新一条，避免新增缓存表。
- “今日”页先请求当天已准备的结果；存在时立即展示，并把三条记录更新为 `shown`。
- 当天无预生成结果时，打开页面后按现有推荐流程即时生成。
- 若打开应用后的位置距离预生成位置超过 20 km、温度跨越现有季节阈值
  （`≤12°C`、`13–24°C`、`≥25°C`），或当日最高降水概率跨过 50% 分界，则自动重新
  生成；否则继续使用 06:30 结果，避免重复消耗 MiniMax。

`outfit_history` 增加 nullable `context_json`，保存粗略经纬度、天气、当地日期、
`prepared_at`，以及还原卡片所需的 `weather_fit` 和 `occasion_fit`。现有五表结构不变；
`init_db()` 对旧 SQLite 执行一次幂等的加列检查。

### 调度边界

后端提供 `python -m outfit_ai.precompute_daily` 命令，定时由部署平台 cron 在同一
运行环境调用，不暴露无鉴权的内部 HTTP 接口。本地开发环境只有在电脑未休眠时才能按时
执行；本次不修改 macOS `launchd` 或系统配置。正式部署时调度器和后端必须常驻，才能
保证 06:30。

## Style DNA 核心标签

### 标签层级

灵感图的每张 VLM 分析仍保留完整结构化证据；长期 Profile 只保留：

- 5–7 个核心风格关键词；
- 最多 3 个近期风格信号；
- 最多 5 个核心色名；
- 现有 `taste_memo`，用于保存比标签更细的搭配偏好和变化。

核心关键词按共性和长期稳定性选择，单件服装名、单次场景、季节词和过细配饰不进入
核心关键词。近期信号可以体现新尝试，但不能覆盖用户置顶的核心标签。

推荐模型接收“核心关键词 + 近期信号 + taste memo + 当次参考图”，不再接收无限累积的
原始标签数组。

### 用户管理

“我的”页 Style DNA 模块默认只显示最多 7 个核心关键词和最多 3 个近期信号。点击
“管理”进入同页覆盖层，不新增主导航页面，支持：

- 置顶：最多 3 个，Style DNA 合并时不得自动移除；
- 隐藏：不显示，也不发送给推荐模型；
- 合并：选择两个近义标签，保存一个规范标签并记录别名。

这些规则和最近一次粗略定位复用 `learned_from_feedback_json`。旧值是字符串数组；新值
使用
`{"version":1,"learnings":[],"recent_style_signals":[],"style_tag_preferences":{...},"last_location":{...}}`
信封。Profile API 仍把 `learned_from_feedback` 暴露为字符串数组，并新增独立的
`recent_style_signals`、`style_tag_preferences` 和 `last_location`；前端不解析内部存储
格式，旧数组读取时自动视作 `learnings`。每次带经纬度请求推荐并成功取得天气后，后端
更新 `last_location`，供次日 06:30 使用。

“AI 契合度”不再显示由评分数量推算出的虚假百分比。反馈不足时显示“正在学习”；存在
真实反馈时显示“已根据 N 次反馈更新”，不制造准确率数值。

### 色板

Style DNA 合并只允许以下规范色名：

`黑色、白色、深蓝色、浅蓝色、灰色、米白色、米黄色、卡其色、棕色、绿色、红色、紫色`

前端使用同一份固定色名到 HEX 映射显示色卡，不再按数组位置回退。无法归一的颜色只显示
文字与中性边框，不显示可能误导的颜色块。

## API 变化

### `GET /api/weather`

请求参数保持 `city`、`latitude`、`longitude`。响应在现有字段上增加城市、当地日期、
时区和降雨字段，不删除旧字段。

### `POST /api/recommend`

请求体新增可选 `force_refresh=false`，旧请求保持兼容。响应中的 `weather` 使用扩展后的
天气结构。默认先复用上下文仍有效的当天 `prepared` 结果；`force_refresh=true` 时重新
生成，避免前端重复拼装缓存规则。

### `GET/PUT /api/profile`

增加：

```json
{
  "recent_style_signals": ["轻量叠穿"],
  "style_tag_preferences": {
    "pinned": ["日系松弛"],
    "hidden": ["商务会议"],
    "aliases": {"日杂休闲": "日系松弛"}
  },
  "last_location": {
    "latitude": 31.230,
    "longitude": 121.474,
    "city": "上海",
    "timezone": "Asia/Shanghai",
    "updated_at": "2026-07-31T08:00:00+08:00"
  }
}
```

Profile 对外继续返回 `style_keywords` 和 `palette`，旧前端数据不会失效。

## 验证

### 后端

- 经纬度天气包含当地日期、时区、温度和降雨字段。
- 反向地理编码失败时仍能返回天气。
- 城市查询和经纬度查询继续兼容。
- 同一天存在 `prepared` 三档时不重复调用 MiniMax。
- 位置/天气发生显著变化时可以强制重新生成。
- Style DNA 合并在有充分证据时保留 5–7 个核心标签；证据不足可以更少但不得超过 7；
  近期最多 3、色板最多 5，并尊重置顶、隐藏和别名。

### 前端

- 390 × 844 手机视口首次打开会触发定位权限；允许、拒绝和超时三条路径均可使用。
- 页面不再出现默认东京；定位成功后显示真实城市、温度和降雨提示。
- 06:30 结果存在时首屏直接展示，不再次调用生成。
- Style DNA 色卡与名称一致，核心标签数量受控，标签管理可持久化。
- “AI 契合度”不再显示伪造百分比。
