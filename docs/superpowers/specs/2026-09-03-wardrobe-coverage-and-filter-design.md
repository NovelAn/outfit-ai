# 衣橱覆盖推荐、人工适穿标签与组合筛选设计

## 背景

云端历史审计确认，每日推荐的问题来自四个环节共同作用：

1. `seasons_json` 由图片识别生成，但图片无法可靠判断克重、里料与真实体感；错误季节标签会在候选阶段直接排除单品。
2. 当前候选池随机截断到 15 件，并固定先取每个必需品类中排序靠前的单品，造成结构性曝光差异。
3. 最近重复逻辑默认跳过鞋履，且只向造型师提供近期 Look，不提供单品使用次数、最后出现时间或从未使用状态。
4. Safe / Fresh / Stretch 只有名称差异；校验只要求三套 item ID 组合不完全相同，不能保证用户感知上的档位差异。

项目目标不仅是生成当天合理的搭配，还要在用户品味和天气允许的范围内持续扩大真实衣橱覆盖率。

## 已确认目标

1. 所有上装、下装、鞋履和配饰都支持人工季节多选：春、夏、秋、冬。
2. 所有品类保留轻薄、适中、厚实三档厚薄标签，并允许人工修改。
3. AI 负责首次识别；用户保存后的季节和厚薄结果是后续筛选与推荐的最终事实。
4. 真实衣橱支持品类、季节、厚薄三个维度的组合筛选。
5. 推荐采用“规则控制候选与覆盖、MiniMax-M3 负责审美搭配”的方案 B。
6. Safe 保持稳妥；Fresh 和 Stretch 分别承担引入长期未使用单品与扩大风格边界的责任。
7. 降低单品高频复用、拒绝近期完全重复的 Look，并在衣橱条件允许时让三档核心单品明显不同。

## 非目标

- 不新增推荐权重表、向量数据库、GNN、FAISS 或新的外部依赖。
- 不让规则判断“哪套更好看”；审美组合仍由 MiniMax-M3 完成。
- 不新增季节或厚薄数据库列；复用 `wardrobe_items.seasons_json` 与 `tags_json`。
- 不自动改写现有用户季节标签。旧标签继续兼容，由用户按需修正。
- 不改动 Style DNA、品味备忘录和反馈刷新机制。

## 1. 标签语义与人工兜底

### 1.1 适用季节

衣橱详情编辑把现有自由文本季节输入改为春、夏、秋、冬多选按钮，适用于全部品类。

- “四季”只作为全选四季的快捷操作，不作为第五个独立值保存。
- AI 首次识别结果映射到四季按钮；已有 `四季`、`全年`、`all` 数据在编辑器中显示为四季全选。
- 用户保存后直接覆盖 `seasons_json`。当前系统不会自动重新识别已确认单品，因此不需要额外的 `manual_override` 字段。
- 未选择任何季节表示缺少限制信息，保持现有兼容行为：全年可进入候选，而不是永久隐藏。

### 1.2 厚薄度

厚薄继续使用 `tags_json` 中互斥的 `轻薄`、`适中`、`厚实` 标签：

- AI 可以给出初始值；用户可改为另一档或清空。
- 保存时移除旧厚薄标签，只保留用户当前选择的一档。
- 厚薄不是独立季节，也不作为跨品类的绝对硬过滤。它与温度、体感温度、湿度和叠穿关系一起传给造型师。
- 高温或高湿时优先轻薄、谨慎使用厚实；低温时优先厚实，轻薄单品必须通过叠穿成立；温和天气允许三档参与。
- 季节仍是候选资格的硬边界，厚薄是天气适穿度指导，避免把轻薄内搭或厚底鞋用同一阈值错误排除。

## 2. 真实衣橱组合筛选

衣橱页使用三个紧凑筛选组：

1. 品类：全部 / 上装 / 下装 / 鞋履 / 配饰，单选。
2. 季节：春 / 夏 / 秋 / 冬，多选；四季为全选快捷按钮。
3. 厚薄：轻薄 / 适中 / 厚实，多选。

筛选逻辑固定为：

- 同一筛选组内为“或”。
- 不同筛选组之间为“且”。
- 未选择某组条件表示该维度不过滤。
- 季节为四季全选时等同于季节不过滤。
- 筛选状态只保存在当前 React 页面会话；刷新或重新进入应用恢复为“全部”。
- 批量管理、全选和相邻单品切换都只作用于当前组合筛选结果。
- 无结果时明确显示“没有符合当前筛选条件的单品”，并提供清除筛选按钮。

示例：“下装 + 春/夏 + 轻薄/适中”表示适合春季或夏季、且厚薄为轻薄或适中的下装。

## 3. 推荐数据流

### 3.1 Stage 1：人工事实与天气资格

候选资格保持确定性：

1. 仅使用 `ready` 且 `confirmed_by_user=true` 的真实单品。
2. 规范化 `seasons_json` 的中英文别名，并按当天季节筛选；人工保存后的值自然覆盖 AI 初始值。
3. 锁定单品继续优先，但仍须存在、状态可用且符合人工季节标签；锁定不能绕过季节硬边界。
4. 不再随机截断到 15 件；当前单用户 v0 将全部应季单品交给造型师，避免候选池先把冷门单品淘汰。
5. 厚薄、气温、体感温度、湿度作为适穿上下文，不在 guardrail 中做跨品类的一刀切排除。

当前真实衣橱规模足以直接传递全部应季单品；只有未来实测出现模型上下文限制时，才增加基于品类和低曝光度的上限策略。

### 3.2 Stage 2：覆盖信息与目标单品

直接从 `outfit_history` 计算每件候选单品的：

- 已展示次数；
- 最后展示日期；
- 是否从未展示；
- 是否出现在最近一组推荐中。

`prepared` 但未被用户看到的记录不计入曝光；`shown`、`saved`、`skipped`、`worn` 均表示已经展示。

排序优先级为：从未展示 → 展示次数更少 → 最后展示时间更早。最近一组已出现的单品降为低优先级，但在衣橱不足时仍可使用。

每天选择两个不同的应季低曝光单品作为覆盖目标：

- Fresh 必须包含第一个覆盖目标。
- Stretch 必须包含第二个覆盖目标。
- 覆盖目标不得与当前另外两档已占用的核心单品冲突；单卡换一换时从剩余低曝光单品中选择下一件。
- Safe 不强制覆盖目标，但造型师仍会收到全部单品曝光信息，避免持续依赖同一件热门单品。
- 用户锁定单品的显式意图高于覆盖与三档差异规则，但不高于人工季节硬边界。

系统停止自动删除旧的普通推荐历史。当前是单用户 SQLite，约每天三条记录，保留历史的成本很低；历史 API 仍使用 `limit` 返回有限记录，不增加前端载荷。已经被删除的旧记录不做恢复。

### 3.3 Stage 3：MiniMax-M3 三档任务

造型师提示词明确写入三档边界：

- Safe：天气合适、符合长期 Style DNA、组合熟悉耐穿；不强制冷门单品，但避免无理由复用最近热门单品。
- Fresh：必须包含指定低曝光单品，在 Style DNA 内改变一个主要维度，例如颜色、廓形、层次或鞋型。
- Stretch：必须包含另一件指定低曝光单品，并在颜色、廓形、搭配公式中至少形成一个比 Fresh 更明显的突破，但不得违反人工季节标签和天气安全。

候选 JSON 为每件单品增加曝光信息与厚薄标签。提示词要求 reason 具体说明 Fresh / Stretch 的新意，不用“更有个性”等空泛文案替代差异。

### 3.4 Stage 4：确定性校验

保留现有真实性与完整性校验，并新增：

- Fresh 与 Stretch 必须包含各自的覆盖目标。
- 最近 30 天出现过的完全相同 item ID 组合直接失败并回灌重试。
- 当应季候选中各有至少三件 top、bottom、shoes 时，同一推荐组的三档不得共用相同上装、下装或鞋履。
- 某必需品类不足三件时允许最小必要共用，避免把可生成场景误报为失败。
- 锁定单品允许突破跨档不共用规则，但必须符合人工季节标签，并在三档中保留现有锁定语义。

校验仍最多重试一次；两次失败返回明确错误，且不写入不完整历史。

## 4. 单卡换一换

- Safe 换一换不强制冷门目标，但不得复制最近 30 天完整 Look。
- Fresh / Stretch 换一换重新选择一个尚未被当前组其他档位使用的低曝光目标。
- 另外两档、其 history ID 与反馈状态保持不变。
- 新结果继续写入当前 `recommendation_set_id`，并参与后续曝光统计。

## 5. API 与存储影响

- `PATCH /api/wardrobe/{id}` 路径和请求结构不变，继续提交 `seasons` 与 `tags`。
- `GET /api/wardrobe/items` 响应结构不变。
- `POST /api/recommend` 请求和响应结构不变；覆盖目标和曝光统计只作为后端内部造型师上下文。
- 不新增数据库表、列或迁移。
- 不新增前端持久化键。

## 6. 失败与边界处理

- 人工季节筛选后缺少上装、下装或鞋履时，返回现有“已确认衣橱不足”错误。
- 某件单品没有厚薄标签时保持可用，由材质、季节和造型师判断，不把缺失值解释为“适中”。
- 季节或标签 JSON 损坏时安全回退为空列表，并按缺少限制信息处理。
- 覆盖目标不足两件时只对可用目标执行强制；不为了满足覆盖加入不应季单品。
- 当天普通推荐继续复用同一完整推荐组，避免刷新页面制造虚假曝光或新组合。

## 7. 验收与测试

### 后端

- 季节别名和四季全选正确参与所有品类过滤。
- 全部应季单品进入造型师上下文，不再随机截断。
- 曝光统计忽略未展示的 prepared 记录，并正确计算次数、最后日期和从未展示。
- 鞋履与其他品类使用相同的近期降权逻辑。
- Fresh / Stretch 缺少覆盖目标时校验失败。
- 最近 30 天完全相同 Look 校验失败。
- 候选充足时三档核心单品不重叠；不足时允许最小必要共用。
- 单卡刷新只替换目标档，并选择未被另外两档占用的覆盖目标。
- 推荐成功后不再清理旧普通历史。

### 前端

- 所有品类都能多选春、夏、秋、冬；四季按钮正确全选和取消。
- 厚薄度最多选择一档，人工保存后重新加载仍一致。
- 品类、季节、厚薄满足组内“或”、组间“且”。
- 批量管理和相邻切换只使用当前筛选结果。
- 无结果状态可以一键清除筛选。
- 390×844 手机视口下三组筛选可操作，不遮挡衣橱卡片和底部导航。

### 线上观察指标

- 最近 30 天完全重复 Look 数为 0。
- 在应季候选足够时，同日三档核心单品重叠数为 0。
- Fresh / Stretch 每个成功生成日各带入一件低曝光目标。
- 应季且从未展示的单品数量随成功生成日持续下降。
